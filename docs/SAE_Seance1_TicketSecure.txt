2. Analyse des besoins – Méthode 5W2H
La méthode 5W2H (What, Why, Who, Where, When, How, How much) permet de cadrer rapidement les besoins du projet avant toute conception technique.
2.1 WHAT – Quoi ?
Développer un système d'information de billetterie en ligne (MVP) permettant :
L'achat de tickets de spectacle en ligne (max 4 tickets/spectacle/compte)
La création et gestion de comptes utilisateurs authentifiés
Le dépôt et la consultation d'avis et de notes sur les spectacles
La consultation du catalogue d'événements (dates, prix, illustrations)
La génération de factures dématérialisées
La récupération de mot de passe en cas d'oubli
2.2 WHY – Pourquoi ?
Objectif pédagogique : concevoir un SI réaliste exposé aux attaques, puis identifier et corriger ses vulnérabilités.
Objectif fonctionnel : fournir une plateforme sécurisée d'achat de billets à des utilisateurs finaux.
Risques à anticiper : injections SQL, détournement de session, fuites de données, malwares, déni de service (DoS), ingénierie sociale.
2.3 WHO – Qui ?
Créateurs : équipe dev (3 personnes) – rôles Backend, Frontend, Sécurité/Docs
Utilisateurs finaux : toute personne souhaitant acheter un ticket de spectacle
Administrateur : gestionnaire de la plateforme (ajout/suppression d'événements)
Attaquants simulés : équipe pirate de la SAÉ (tests de pénétration)
2.4 WHERE – Où ?
Développement local : machines personnelles (Windows/Linux/Mac) + VM si besoin
Backend : serveur Flask (Python) sur localhost puis potentiellement hébergé
Base de données : SQLite en développement, migration possible vers MySQL
Versionnement : dépôt GitLab UPHF – https://gitlab.uphf.fr/<groupe>/ticketsecure
Maquettes : Figma (version gratuite)
Diagrammes : PlantUML
2.5 WHEN – Quand ?
Phase 1 (séance 1) : Analyse des besoins, conception préliminaire → livrable ZIP
Phase 2 (séances 2-3) : Conception détaillée – base de données, routes Flask, maquettes
Phase 3 (séances 4-5) : Développement MVP + tests unitaires + premières attaques
Phase 4 (séance 6) : Formation utilisateurs, documentation sécurité
Phase 5 (séance 7+) : Maintenance, audit de sécurité, présentation orale finale
2.6 HOW – Comment ?
Backend : Python 3 + Flask (routing, sessions, Jinja2) + SQLAlchemy ou sqlite3
Frontend : HTML5, CSS3, JavaScript vanilla (MVP – pas de framework JS lourd)
Sécurité : bcrypt (hachage MDP), tokens CSRF, HTTPS (auto-signé en dev), validation serveur, gestion des sessions sécurisées
Récupération MDP : token temporaire signé envoyé par e-mail (SMTP ou Mailhog en dev)
Modélisation : PlantUML pour cas d'utilisation et diagrammes d'activité
Maquettes : Figma (wireframes basse fidélité)
CI/CD : GitLab CI basique (lint + tests automatiques)
2.7 HOW MUCH – Combien ?
Coût financier : nul (outils open-source, hébergement académique UPHF)
Logiciels nécessaires : Python 3.11+, Flask, SQLite, Git, PlantUML, Figma (gratuit), VS Code
Connaissances requises : Python/Flask, SQL, HTML/CSS/JS, bases de la cybersécurité (OWASP Top 10)
Charge estimée : ~30h/personne sur l'ensemble du projet (hors présentations)
Risques projet : complexité sécurité sous-estimée → buffer de 20% prévu

4. Conception préliminaire
4.1 Données nécessaires
Compte utilisateur
id_utilisateur (PK, auto-increment)
email (unique, NOT NULL) – identifiant de connexion
mot_de_passe_hash (bcrypt, NOT NULL)
nom, prenom (NOT NULL)
date_naissance (pour vérification d'âge si nécessaire)
telephone (optionnel)
adresse_facturation (rue, code postal, ville, pays)
token_reset_mdp + expiration_token (récupération MDP)
date_inscription, derniere_connexion
est_actif (booléen – compte vérifié par e-mail)
role (utilisateur / administrateur)
Spectacles & Événements
id_spectacle (PK)
titre, description
date_heure, lieu
prix_unitaire
capacite_totale, places_restantes
illustration_url (image affiche)
categorie (concert, théâtre, danse…)
Commandes & Tickets
id_commande (PK), id_utilisateur (FK), id_spectacle (FK)
quantite (1 à 4 max, contrainte CHECK)
montant_total
date_commande, statut (en_attente / confirmé / annulé)
numero_facture (généré automatiquement)
code_qr_ticket (identifiant unique par ticket)
Avis & Notes
id_avis (PK), id_utilisateur (FK), id_spectacle (FK)
note (1 à 5)
commentaire (texte, taille limitée)
date_avis
est_valide (modération basique)
4.2 Architecture technique envisagée
L'architecture suit le patron MVC (Modèle-Vue-Contrôleur) via Flask :
Modèle : SQLite (dev) avec SQLAlchemy ORM – entités Utilisateur, Spectacle, Commande, Avis
Vue : Templates Jinja2 (HTML/CSS) – pages publiques + espace personnel authentifié
Contrôleur : Blueprints Flask (auth, catalogue, commandes, admin, avis)
Sécurité : Flask-Login (sessions), Flask-WTF (CSRF), Werkzeug (bcrypt), Flask-Limiter (rate limiting)
E-mails : Flask-Mail (SMTP) ou Mailhog en développement local
4.3 Procédures de sécurité prévues
Procédure
Mise en œuvre
Création de mot de passe sécurisé
Minimum 12 caractères, majuscule + minuscule + chiffre + symbole. Hachage bcrypt (coût 12). Interdiction des 10 MDP les plus courants (liste HIBP).
Oubli de mot de passe
Token aléatoire (secrets.token_urlsafe) stocké hashé en BDD, valide 30 min. Envoi lien unique par e-mail. Invalidation après usage ou expiration.
Vérification de compte
E-mail de confirmation à l'inscription. Token signé (itsdangerous). Compte inactif jusqu'à validation.
Verrouillage après tentatives
5 tentatives de connexion échouées → compte verrouillé 15 min. Log des tentatives. Alertes admin si attaque détectée.
